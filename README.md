# ระบบติดตามรถในอาคารจอดรถ (Vehicle Fingerprint) — เอกสารออกแบบ

วันที่: 2026-11-18 · สถานะ: รออนุมัติ

## 1. เจตนาและเหตุผล

เจ้าของระบบต้องการให้ระบบ "ตามได้ว่ารถคันนี้ไปโผล่ที่ไหนบ้าง เมื่อวันนี้เวลานั้น และค้นหาได้" ในอาคารจอดรถหนึ่งตึก
ระบบบันทึกทุกครั้งที่กล้องเห็นรถ แล้วให้คนค้นย้อนหลังเพื่อดูเส้นทางของรถตั้งแต่เข้าจนออก

สิ่งที่เจ้าของระบบกำหนดเอง:
- เริ่มที่รถก่อน ใช้ Vehicle Fingerprint (ยี่ห้อ รุ่น สี ลักษณะเด่น) ร่วมกับป้ายทะเบียน
- ต้องขยายระบบได้ในอนาคต (เช่น จับ "คน" หรือวัตถุอื่น)
- ใช้กล้องรุ่นเดียวกันทั้งอาคาร เพื่อรองรับหลายมุม
- ตึกเดียว GPU เครื่องเดียว

## 2. เป้าหมาย / ไม่ใช่เป้าหมาย / สิ่งที่ถือว่าล้มเหลว

**เป้าหมาย**
- ค้นด้วยเลขป้าย (ทนต่อ OCR ผิดบางตัว), ช่วงเวลา, จุดกล้อง, สี/ประเภทรถ, หรือภาพรถ
- แสดงเส้นทางของรถตามลำดับเวลา พร้อมภาพประกอบทุกจุด
- เพิ่มกล้องหรือเพิ่มชนิดวัตถุที่จับได้โดยไม่ต้องรื้อส่วนเก็บและค้นหา

**ไม่ใช่เป้าหมาย (รุ่นแรก)**
- ไม่ทำระบบเก็บเงิน/ไม้กั้น/คิดค่าจอด
- ไม่ทำระบบหลายตึกหรือหลายสาขา
- ไม่จับคนและไม่ทำ face recognition

**สิ่งที่ถือว่าล้มเหลวแม้ระบบทำงานได้**
- ระบบบอกว่า "แน่ใจ" ทั้งที่เดา (การเทียบด้วยลักษณะรถต้องแสดงระดับความมั่นใจเสมอ)
- ระบบกลายเป็นเครื่องมือสืบค้นที่ใครก็เปิดดูได้โดยไม่มีบันทึกการเข้าถึง

## 3. ข้อจำกัด

- ตึกเดียว, GPU เครื่องเดียว, กล้องรุ่นเดียวกัน (จำนวนกล้องยังไม่ระบุ)
- ป้ายทะเบียนไทย: อักษรไทย ชื่อจังหวัด ป้ายหลายแบบ โมเดล OCR สำเร็จรูปส่วนใหญ่ไม่ได้ฝึกมากับป้ายแบบนี้
- PDPA: ป้ายทะเบียนที่ผูกกับเวลาเข้า-ออกเป็นข้อมูลส่วนบุคคล ต้องมีวัตถุประสงค์ ระยะเก็บ และสิทธิ์เข้าถึง

## 4. แนวทางที่พิจารณา

| แนวทาง | สรุป | ข้อแลกเปลี่ยน |
|---|---|---|
| A. Edge | กล่องเล็กข้างกล้องทุกจุดอ่านภาพเอง | ต้นทุนต่อจุดสูง อัปเดตโมเดลยาก |
| B. ศูนย์กลาง | วิดีโอทั้งหมดเข้า GPU เครื่องเดียว | ถูก ง่าย แต่ขยายยากและเป็นจุดล้มเหลวจุดเดียว |
| **C. เริ่มแบบ B ออกแบบให้ย้ายไป A ได้** | แยก "อ่านภาพ" ออกจาก "เก็บและค้นหา" ด้วยข้อกำหนด event ตายตัว | ต้องทำข้อกำหนดข้อมูลให้รอบคอบตั้งแต่ต้น |

**เลือก C** (เจ้าของระบบเลือกขนาด "ตึกเดียว GPU เดียว" ซึ่งเข้ากับ C)

## 5. สถาปัตยกรรม

```
กล้อง (RTSP) ─► [Ingest] ─► [Detector+Tracker] ─► [Readers] ─► Sighting event ─► [Queue]
                                                                                   │
                                                          [Linker: ต่อเส้นทางข้ามกล้อง]
                                                                                   │
                                                          [Store: Postgres+pgvector + ที่เก็บภาพ]
                                                                                   │
                                                                    [Search API] ─► [เว็บค้นหา]
```

**ส่วนที่ 1 อ่านภาพ (รันบน GPU)**
- Ingest: รับ RTSP ต่อกล้อง ถอดรหัส ลดเฟรมเรตตามความจำเป็น
- Detector+Tracker: ตรวจรถและป้ายในเฟรม ติดตามรถคันเดิมภายในกล้องตัวเดียวกัน
- Readers: ปลั๊กอินที่รับภาพรถที่ตัดแล้ว คืนค่าลักษณะ รุ่นแรกมี 2 ตัว คือ PlateReader (OCR ป้าย) และ VehicleAttributeReader (สี ประเภท ยี่ห้อ/รุ่นถ้าทำได้ พร้อม embedding)

**ส่วนที่ 2 เก็บและค้นหา (ไม่รู้ว่าภาพมาจากไหน)**
- รับเฉพาะ Sighting event จากคิว ไม่ต่อกับกล้องโดยตรง

**จุดที่ทำให้ขยายได้**
- `subject_type` ใน event เป็น `vehicle` ในรุ่นแรก เพิ่ม `person` หรืออื่นๆ ได้โดยเพิ่ม Reader ใหม่ ไม่แก้ส่วนเก็บ
- ถ้าอยากย้ายการอ่านภาพไปไว้ที่กล้อง ส่วนที่ 2 ไม่ต้องแก้ เพราะรับ event รูปแบบเดิม

### Sighting event (ข้อกำหนดหลัก)

```
sighting_id, camera_id, observed_at (เวลาสากล), subject_type
track_id (ภายในกล้อง)
plate: { text, province, confidence }          // ว่างได้
attributes: { color, vehicle_type, make, model, ... } + confidence แต่ละตัว
embedding: เวกเตอร์ลักษณะรถ                      // ว่างได้
images: { crop_path, context_path }
reader_versions: { plate: "x", attr: "y" }     // ไว้ย้อนดูว่าใช้โมเดลรุ่นไหน
```

### การต่อเส้นทางข้ามกล้อง (Linker)

ลำดับความน่าเชื่อถือ:
1. ป้ายตรงกันเป๊ะ → ต่อเป็นคันเดียวกัน (มั่นใจสูง)
2. ป้ายใกล้เคียง (OCR ผิด 1-2 ตัว) และสี/ประเภทตรงกัน → ต่อพร้อมติดป้าย "ป้ายคล้าย"
3. ป้ายอ่านไม่ได้ → ใช้ embedding + ลักษณะรถ + ข้อจำกัดเชิงพื้นที่ (กล้องที่อยู่ติดกัน, เวลาที่เป็นไปได้) → ต่อพร้อมติดป้าย "เดา" และแสดงคะแนน

กล้องที่อยู่ติดกันและเวลาเดินทางขั้นต่ำกำหนดไว้ในไฟล์ตั้งค่าผังอาคาร (topology) ดู `deploy/topology.example.toml` และ `api/README.md`

## 6. การค้นหา

- เลขป้าย (ค้นแบบทนข้อผิดพลาด), วันที่และช่วงเวลา, จุดกล้อง, สี/ประเภทรถ
- ค้นด้วยภาพ: อัปโหลดภาพรถ หาคันที่คล้ายที่สุด
- ผลลัพธ์เป็นไทม์ไลน์ต่อคัน พร้อมภาพและป้ายสถานะความมั่นใจ (ชัด / ป้ายคล้าย / เดา)

## 7. ความเป็นส่วนตัวและความปลอดภัย

- ระยะเก็บ: ภาพและ event เก็บ 30 วันแล้วลบอัตโนมัติ (ข้อเสนอของผู้ออกแบบ รอเจ้าของระบบยืนยัน)
- สิทธิ์: มีบัญชีผู้ใช้และบทบาท ทุกการค้นหาถูกบันทึกใน audit log (ใคร ค้นอะไร เมื่อไร)
- ไม่ทำ face recognition; ภาพคนที่ติดมาในภาพรถไม่ถูกวิเคราะห์
- ติดป้ายแจ้งว่ามีกล้องในพื้นที่ และเตรียมนโยบายความเป็นส่วนตัวตาม PDPA
- เข้ารหัสการเชื่อมต่อและที่เก็บข้อมูล

## 8. ส่วนที่ผู้ออกแบบเลือกเอง (เจ้าของระบบยังไม่ได้ตกลง)

รายละเอียดเต็มอยู่ใน [STACK.md](STACK.md)

- ภาษาและเฟรมเวิร์ก: Python (ประมวลผลภาพ), FastAPI (API), React (หน้าเว็บ)
- ฐานข้อมูล: Postgres + pgvector + pg_trgm, แบ่ง partition ตามวัน
- คิว: Valkey Streams (เข้ากันได้กับ Redis, ใบอนุญาต BSD) เพราะอยู่เครื่องเดียว
- Detector: RT-DETR หรือ YOLOX (Apache-2.0) ไม่ใช้ Ultralytics YOLO เพราะเป็น AGPL-3.0
- Tracker: ByteTrack
- ที่เก็บภาพ: filesystem ผ่าน interface ให้ย้ายไป object storage ได้
- OCR ป้ายไทย: ต้องฝึกหรือปรับจูนด้วยภาพจากกล้องจริงของอาคารเอง ไม่พึ่งโมเดลสำเร็จรูปอย่างเดียว
- ระยะเก็บข้อมูล 30 วัน

## 9. ปล่อยให้ผู้สร้างตัดสินใจ

- จำนวนเฟรมต่อวินาทีที่ประมวลผลต่อกล้อง (วัดจาก GPU จริง)
- รูปแบบโครงสร้างไฟล์ภาพและชื่อไฟล์
- หน้าตาและรายละเอียด UI

## 10. ความเสี่ยงและสิ่งที่ยังไม่รู้

- **จำนวนกล้องและรุ่น GPU ยังไม่ระบุ** ความจุจริงต้องวัดหลังได้ภาพจริง จึงยังไม่ให้ตัวเลขว่ารองรับกี่กล้อง
- ความแม่นยำ OCR ป้ายไทยในตอนกลางคืน ไฟหน้ารถ และมุมเอียง ยังไม่รู้จนกว่าจะทดสอบ
- ลักษณะรถแบบ "ยี่ห้อ/รุ่น" อาจแม่นไม่พอในบางรุ่น รุ่นแรกอาจใช้แค่สีและประเภทรถเป็นหลัก

## 11. ลำดับการสร้างที่เสนอ

1. **ทดสอบความเป็นไปได้:** เก็บภาพจากกล้องจริง 1-2 จุด วัดความแม่นยำป้ายและความเร็วบน GPU
2. **กล้องเดียวครบวงจร:** อ่านภาพ → event → เก็บ → ค้นด้วยป้าย
3. **หลายกล้อง:** Linker + ผังอาคาร + ไทม์ไลน์เส้นทาง
4. **ใช้งานจริง:** บัญชีผู้ใช้ audit log ลบข้อมูลอัตโนมัติ การเฝ้าระวังระบบ
5. **ภายหลัง:** Reader ใหม่ (เช่น คน) หรือย้ายการอ่านภาพไปไว้ที่กล้อง
